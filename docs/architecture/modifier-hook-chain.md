## Context

**Problem Statement** (inferred): a Hearthstone-style match needs a single place
where run-level buffs (treasures, upgrades, weekly-schedule effects) can alter
numbers and veto actions across every system — card cost, damage, healing, mana,
targeting, keyword strength, shop prices — without each system knowing which buffs
exist.

**Background** (inferred from code):
- The prototype's run loop (week runner, shop, victory draft) and its match loop
  both call the same manager, so one mechanism was meant to span both.
- `ModifierDisplay`'s doc comment says "show the player their active buffs":
  the design assumed **one player's** buffs, which is why nothing is scoped per
  player (see Known Issues).
- Hooks for a "weekly schedule system" and "class resources" exist with no
  caller for the latter — the base class was written ahead of the systems it
  served. `INTENT UNKNOWN — inferred from implementation, not confirmed.`

**System Scope**: `autoload/modifier_manager.gd` (singleton), `scripts/modifier.gd`
(base class), `scripts/modifier_registry.gd` (template catalogue),
`scripts/modifier_display.gd` (HUD). Called from `game_manager.gd` (34 sites),
`minion.gd` (8), `card_effect_base.gd` (12), `player_controller.gd` (3),
`week_runner.gd` (5), `shop_screen.gd` (1), `victory_selection.gd` (3).

**Stakeholders**:
- Systems design: needs treasures that compose predictably (order, stacking, duration).
- Gameplay programming: needs the rules engine free of per-treasure branches.
- QA: needs every hook deterministic and unit-testable (not possible as built — see Validation).

## Decision

**Approach Taken** (as implemented):

A global singleton (`ModifierManager`, a `Node` autoload) owns a dictionary of
active `Modifier` instances keyed by `id`. Every game system that computes a
tunable number or asks permission for an action calls a typed manager method
(`apply_*`, `trigger_*`, `can_*`, `filter_targets`). The manager iterates the
active modifiers **in descending `priority` order** and calls the matching
virtual method on each. `Modifier` is a `Resource` subclass declaring ~36 no-op
virtual hooks; a concrete modifier overrides only the hooks it cares about.

**Key Implementation Details**:

- **Three hook shapes, one ordering** (`modifier_manager.gd:152–188` and each `#region`):
  | Shape | Manager method prefix | Combination rule | Example |
  |---|---|---|---|
  | Trigger (void) | `trigger_*` | call every enabled modifier that `has_method`, via `callv` | `on_minion_death(minion, player_index, killer)` |
  | Value chain (int / Array) | `apply_*`, `filter_targets` | **fold**: output of modifier *n* is the input of modifier *n+1*; then a clamp | `modify_card_cost(card, cost, player_index)` |
  | Gate (bool) | `can_*` | **AND, short-circuit**: first `false` wins | `can_minion_attack(minion, target)` |
- **Priority**: `@export var priority: int = 0`; sorted "higher first" with
  `Array.sort_custom` (`:146`) on `priority` alone, so **the code defines no
  order for equal priorities** — whatever `sort_custom` does with ties is what
  happens. `NOT SOURCEABLE — whether Godot 4.7's sort_custom is a stable sort is
  not covered by docs/engine-reference/godot/`; do not rely on it either way.
  `INTENT UNKNOWN` whether ties were meant to be insertion order.
- **Dirty-flagged cache**: `_sorted_modifiers` is rebuilt only when
  `_cache_dirty` is set by add/remove/load (`:137–147`); every hook entry calls
  `_refresh_cache_if_needed()` first.
- **Template → instance**: the registry holds template resources;
  `add_modifier` stores `modifier.create_instance()` = `duplicate(true)` +
  `on_added()` (`modifier.gd:301`). The manager then calls `instance.on_added()`
  a second time (`modifier_manager.gd:62`) — harmless today because `on_added`
  only resets `_turns_remaining`, but a double-fire.
- **Stacking**: same `id` already active → `stacks += incoming.stacks`, clamped
  to `max_stacks` (`0` = unlimited); `on_stack_added(new_total)` fires and
  `modifier_stacks_changed` is emitted. At max, `add_modifier` returns `false`.
  `remove_stack(id, count)` removes the modifier entirely at 0.
- **Duration**: `duration_turns > 0` → `on_turn_end` decrements
  `_turns_remaining` **regardless of `player_index`** and, at 0, the modifier
  removes itself with `ModifierManager.remove_modifier(id)` (`modifier.gd:77`) —
  the back-reference to the singleton.
- **Enable flag**: `is_enabled == false` skips the modifier in every chain but
  keeps it registered (and saved).
- **Clamps applied after the chain** (manager side, not in the modifier):
  card cost ≥ 0, card attack ≥ 0, card health ≥ 1, minion attack ≥ 0, minion
  health ≥ 1, hero-power cost ≥ 0, mana gain ≥ 0, class-resource cost ≥ 0.
  **Not clamped**: damage dealt/taken, healing, class-resource gain, keyword
  value, schedule effect — a negative result is passed through.
- **Observability**: signals `modifier_added`, `modifier_removed`,
  `modifier_stacks_changed`, `modifiers_cleared`; `ModifierDisplay` subscribes
  and renders a 48×48 icon per modifier with stack count and turns-left label.
- **Persistence**: `get_save_data()` → `{id: {stacks, turns_remaining, is_enabled}}`;
  `load_save_data(data, registry_dict)` re-instances from templates **without**
  calling `on_added` (so saved `turns_remaining` survives) and emits
  `modifier_added` per entry.
- **Lifecycle vs match**: `GameManager.start_game()` calls
  `ModifierManager.clear_all_modifiers()` (`game_manager.gd:137`), so in the
  prototype **no modifier can survive into a duel** — the run-persistence the
  schedule hooks imply never worked end to end. `INTENT UNKNOWN` whether the
  clear was meant for "Test Duel" only.

## Alternatives Considered

*(Inferred — none are documented in the prototype.)*

### Alternative 1: Per-system branching on modifier ids

**Description**: each system checks `if run.has("double_drain")` inline.

**Pros**: no framework; trivially debuggable.
**Cons**: every new treasure touches every system it affects; no ordering or stacking rules.
**Why Not Chosen** (inferred): the hook catalogue shows the author wanted treasures to be addable without editing the rules engine.

### Alternative 2: Event bus with unordered subscribers

**Description**: systems emit signals; modifiers connect and mutate shared state.

**Pros**: idiomatic Godot; fully decoupled.
**Cons**: value-modifying hooks need a return value and an order; signals give neither.
**Why Not Chosen** (inferred): the value-chain hooks (`modify_*`) return the next input, which a signal cannot express; the manager keeps signals only for observers (`ModifierDisplay`).

### Alternative 3: Status quo (no modifier system)

**Description**: ship the match with fixed numbers.
**Why Not Acceptable**: the run structure (shop upgrades, reward buckets, side-job gold) had nothing to buy.

## Consequences

### Positive Consequences (observed)

✅ **One integration surface**: 60+ call sites, each a single line (`result = ModifierManager.apply_x(...)`), with no per-treasure logic in the rules code.

✅ **Deterministic composition when priorities differ**: the fold makes "+2 then ×2" vs "×2 then +2" an explicit `priority` choice, not an accident of registration order.

✅ **Content is data**: a treasure is a `Resource` (template) granted by id from a registry, duplicated per grant, and serialisable (`stacks`, `turns_remaining`, `is_enabled`).

✅ **Stacking and duration are solved once**, in the manager/base class, not per treasure.

### Negative Consequences (observed)

⚠️ **Global, not owner-scoped**: one dictionary for the whole game. A cost reduction granted to the player also reduces the opponent's costs unless the subclass inspects `player_index` itself — and five hook families (`combat_*`, `damage_*`, `healing`, `minion_*`, `targeting`) carry no `player_index` at all, so a subclass **cannot** scope them. For a run game with per-player treasures this is a design defect, not a tuning issue.

⚠️ **Back-reference to the singleton**: `modifier.gd:77` calls `ModifierManager.remove_modifier(id)` from inside a hook. The base class therefore cannot be instantiated or tested without the autoload, and a modifier held by two managers would remove itself from the wrong one.

⚠️ **Scene-tree coupling**: 16 hook parameters are typed `Node` (minions, sources, targets). Nothing here can run headless against plain data.

⚠️ **Duration counts both players' turn ends**: `on_turn_end(player_index)` ignores the index, so "lasts 2 turns" expires after one full round. `INTENT UNKNOWN` whether "turn" meant round.

⚠️ **Duck-typed dispatch**: trigger and gate helpers use `has_method` + `callv`, so a misspelled override silently never runs; the `apply_*` chains call the method directly and would fail loudly.

⚠️ **Undefined tie order**: two treasures at the same `priority` compose in an order the code does not specify (see Decision; sort stability is `NOT SOURCEABLE` from the engine reference).

### Neutral Consequences (observations)

ℹ️ The `_execute_int_hooks` generic helper exists but every `apply_*` method re-implements its loop inline (14 copies) — duplication the rewrite should not carry.

ℹ️ `get_all_modifiers()` returns a `duplicate()` each call; `ModifierDisplay._refresh_all` and `print_active_modifiers` are the only readers.

## Implementation Notes

**Patterns Used**:
- Singleton (autoload) — the manager.
- Template Method / virtual hooks — `Modifier` base class; concrete modifiers override.
- Chain of Responsibility (fold variant) — ordered `apply_*` pipelines.
- Prototype — `create_instance()` duplicates a template per grant.
- Observer — four signals for the HUD.
- Registry — `ModifierRegistry` id → template.

**Dependencies Introduced**: every caller depends on the autoload by name; `Modifier` depends on `ModifierManager` (circular at the class level); `ModifierDisplay` depends on both.

**Performance Characteristics**:
- Each hook call is O(n) over active modifiers; the sort is O(n log n) and runs only when dirty.
- `has_method` string lookups on every trigger/gate per modifier per event; negligible at the handful of treasures a run holds (no tuning value states a cap).
- No allocation in the hot path except `filter_targets` (one `duplicate()` per call) and `get_all_modifiers`.

**Thread Safety**: none; main thread only, as all Godot scene code.

**Testing Strategy**: none exists (TD-012). As built, testing requires the autoload and `Node` fixtures.

**Tuning values found in the source** (defaults, with use site): `priority = 0` (sort key), `stacks = 1`, `max_stacks = 0` → unlimited (`modifier_manager.gd:42`), `duration_turns = 0` → permanent (`modifier.gd:74`), card/minion health floor `1`, cost/attack/mana floor `0` (manager clamps).

**Formulas found in the source**:
- `value_out = clamp(fold(modifiers sorted by priority desc, value_in, m.modify_x))` for every `apply_*`.
- `allowed = AND(m.can_x for m in sorted modifiers)` with short-circuit.
- `stacks_new = min(stacks_old + incoming, max_stacks)` when `max_stacks > 0`, else `stacks_old + incoming`.
- `_turns_remaining -= 1` per `on_turn_end` of either player; removal at `<= 0`.

## Validation

**How We Know This Works**: ⚠️ we do not. No concrete modifier, no test and no scene exercises the system; the match loop it is wired into does not run (TD-002/TD-003). What is validated is only that the code parses and that the pattern is consistent across its 60+ call sites.

**Known Issues** (discovered during analysis):
- ⚠️ Not owner-scoped (above) — blocks per-player treasures outright.
- ⚠️ `modifier.gd:77` back-reference — blocks isolated testing and multi-owner managers.
- ⚠️ `clear_all_modifiers()` at every `start_game()` — run modifiers cannot reach a duel.
- ⚠️ Double `on_added()` on grant.
- ⚠️ Unclamped negative damage/healing/keyword values.
- ⚠️ Duration ignores whose turn ended.
- ⚠️ `ModifierDisplay` reaches into `modifier._turns_remaining` (private by convention).

**Risks**: the hook catalogue is wide (36 hooks) for a system with no content; carrying it wholesale into production invites speculative generality. The production ADR should start from the treasures GDD's actual needs and add hooks as stories require them.

## Follow-Up Work

**Requirements the production version must meet** (from this analysis and the prototype README; these are constraints, not open questions):
- [ ] **Owner-scoped**: a modifier set is owned by a player (match scope) or a run (run scope); every hook knows its owner without inspecting arguments. No global singleton.
- [ ] **No back-reference**: a modifier never holds or calls its manager. Expiry is the manager's job (it reads `turns_remaining`, it removes), or the hook returns an "expired" result.
- [ ] Hooks operate on plain data (ids, `RefCounted` state), never `Node`s, so the chain is unit-testable headless.
- [ ] Stable, documented tie-breaking (priority, then grant order).
- [ ] Duration semantics defined per treasure in the GDD (own turn vs round).
- [ ] Run modifiers survive match start; match-scoped ones are cleared at match end.
- [ ] Every value chain states its clamp explicitly in the GDD.

## Engine Compatibility

- **Pinned engine**: Godot 4.7.2 (`docs/engine-reference/godot/VERSION.md`); the prototype was written for Godot 4.5.
- **APIs the pattern relies on**: autoload singletons, `Resource.duplicate(true)`,
  `Array.sort_custom`, `Object.has_method` / `callv`, signals, `@export`. All
  predate 4.4 and the prototype README records no 4.5+ feature in use.
- **One deprecation applies**: `create_instance()` uses `duplicate(true)` to copy
  a template whose fields may hold nested resources (`icon`, and any sub-resource a
  concrete treasure adds). `docs/engine-reference/godot/deprecated-apis.md:33`
  lists `duplicate()` for nested resources as deprecated since 4.5 in favour of
  `duplicate_deep()`; `current-best-practices.md:119–123` says the old behaviour
  is retained but `duplicate_deep()` is the call for per-instance copies of
  nested resources. The production version uses `duplicate_deep()` (or does not
  clone resources at all — see Follow-Up Work). The engine reference was grepped
  for `sort_custom`, `duplicate(`, `callv`, `has_method`: those two lines are
  the only hits.
- **Not sourceable**: sort stability of `sort_custom` (see Decision). The
  production design must not depend on it.
- **Production note**: a rewrite on plain `RefCounted` data needs none of the
  `Node` typing above, which removes the scene-tree dependency entirely.

## Appendix: Code Snippets

**Key Implementation Pattern** — the value chain (`modifier_manager.gd:263–270`):

```gdscript
func apply_card_cost_modifiers(card_data: Resource, base_cost: int, player_index: int) -> int:
	_refresh_cache_if_needed()
	var result := base_cost
	for modifier in _sorted_modifiers:      # sorted by priority, higher first
		if not modifier.is_enabled:
			continue
		result = modifier.modify_card_cost(card_data, result, player_index)  # fold
	return maxi(0, result)                  # clamp after the chain
```

**Rationale** (inferred): each modifier sees the value as left by higher-priority modifiers, so additive and multiplicative treasures compose in a declared order.

**The defect the production version removes** (`modifier.gd:72–77`):

```gdscript
func on_turn_end(player_index: int) -> void:
	if duration_turns > 0:
		_turns_remaining -= 1            # ignores player_index
		if _turns_remaining <= 0:
			ModifierManager.remove_modifier(id)   # back-reference to the global singleton
```

**Why Not**: the modifier decides its own removal from a manager it names globally; the production design keeps expiry in an owner-scoped manager and leaves the modifier as inert data.
